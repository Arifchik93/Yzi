# Идеи по «зависимым» заключениям (без нейросетей)

## Что уже есть в проекте

- Протоколы хранятся в JSON-файлах (`*.txt`) как набор `blocks` с текстом и списками вариантов в `{ ... / ... }`.
- Фронтенд в `app.js` уже умеет разбирать шаблон на сегменты, рендерить поля и собирать финальный текст.

Это хорошая база для полуавтоматического формирования заключения: можно добавить слой **правил**, который будет анализировать выбранные пункты описательной части.

---

## Подход 1 (рекомендуемый): rule-engine для заключения

Добавить в шаблон новый блок, например `type: "conclusion"`, и набор правил:

```json
{
  "type": "conclusion",
  "title": "Заключение",
  "rules": [
    {
      "when": [
        {"field": "ln.form", "in": ["округлой формы", "неправильной полицикличной формы"]},
        {"field": "ln.kmd", "notIn": ["КМД сохранена. КМИ менее 0.5"]}
      ],
      "add": "Эхографические признаки патологически изменённых лимфатических узлов."
    },
    {
      "when": [
        {"field": "ln.form", "in": ["овальной формы"]},
        {"field": "ln.kmd", "in": ["КМД сохранена. КМИ менее 0.5"]}
      ],
      "add": "УЗ-признаки реактивных изменений лимфатических узлов."
    }
  ],
  "fallback": "Убедительных эхографических признаков значимой патологии не выявлено."
}
```

### Ключевая идея

Списки в описании должны иметь **стабильные ключи**, чтобы на них ссылались правила (например, `ln.form`, `ln.kmd`, `ln.vascular`).

### Плюсы

- Понятно врачу и администратору шаблонов.
- Легко валидировать и поддерживать.
- Предсказуемо (нет «магии»).

---

## Подход 2: «каталог признаков» + группировка в синдромы

1. Каждый выбор в описании помечается тегами, например:
   - `benign_like`
   - `suspicious`
   - `inflammatory`
2. Далее простая логика:
   - если есть 2+ `suspicious` → добавить фразу про патологический характер;
   - если есть `inflammatory` и нет `suspicious` → реактивные изменения;
   - если только `benign_like` → без значимых изменений.

### Когда полезно

Когда много протоколов и хочется переиспользовать правила между органами.

---

## Подход 3: «конструктор заключения» из слотов

Заключение собирать из 3 слотов:

- **Основной итог** (норма / реактивные / патологические изменения)
- **Локализация** (слева / справа / билатерально)
- **Уточнение степени выраженности** (единичные / множественные / конгломерат)

Пример:

> «Эхографические признаки [патологических изменений] лимфатических узлов [с обеих сторон], [с формированием конгломерата]».

Это уменьшает число готовых фраз и делает систему стабильной.

---

## Практично для текущего кода (минимальные изменения)

1. В шаблонах дать ключи «важным» полям описания.
2. При выборе значений сохранять структуру `selectedValuesByKey`.
3. Добавить функцию `buildConclusion(selectedValuesByKey, rules)`.
4. Вызывать её при любом изменении формы и выводить блок «Заключение» рядом с общим текстом.
5. Добавить ручной редактируемый хвост: «+ комментарий врача», чтобы врач мог дописать нюансы.

---

## Важные UX-детали

- Показывать, **почему** появилась фраза (например, «сработало правило №3»).
- Кнопка «Сбросить автозаключение».
- Переключатель: «автодополнение включено/выключено».
- Подсветка конфликтов (например, одновременно признаки нормы и грубой патологии).

---

## Безопасность и контроль качества

- Хранить правила в версии (git), изменения — через ревью.
- На каждый протокол сделать мини-набор тест-кейсов «выборы → ожидаемое заключение».
- Запретить публикацию шаблона, если нет `fallback` заключения.

---

## Рекомендуемый план внедрения

1. Пилот на одном протоколе (например, лимфоузлы).
2. 10–20 клинических сценариев с проверкой врача.
3. Корректировка правил.
4. Масштабирование на остальные протоколы.

Так вы получите частично автоматическое, прозрачное и управляемое формирование заключений без использования нейросетей.
